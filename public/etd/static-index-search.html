Static Index Search

We propose a standard way to make any archive.org item searchable in the browser, with no search servers. An item publishes a few index files; a shared engine reads small slices of them; archive.org's existing search UI shows the results. The ETD theses search proves it at 26 million records.

Draft of 29 October 2026 · Isa, with the ETD port in iaux-collection-browser · numbers measured on the live etd-search item

What we propose

  • A published file contract: what an item must publish to be searchable.
  • One shared engine that reads any item following it.
  • A thin adapter so collection-browser shows it like any other search.

Why

  • Searching a dataset today needs it indexed by a central service, or a custom backend.
  • This needs neither: publishing files is enough. Nothing to host, scale or keep running.
  • ETD already works this way and matches its own live page exactly.

What we need

  • Agreement on the contract and who owns it.
  • Help from the ETD index owner on 4 changes (CORS, an id map, published layouts, leaner vectors).
  • A decision on where the engine lives.

1. How it works

A search index is just files. If they're laid out so that answering a query needs only a few small slices, a browser can fetch those slices from archive.org with HTTP Range requests and do the rest itself.

No backend is a hard rule. When a feature is too heavy, we change what the item publishes or do more work in the browser; we never add a service.

Three parts: the item's files (built once per index version), a shared engine that knows the file formats but no particular item, and an adapter plus config per item.

Trade-offs

  • Gains: any item becomes searchable by publishing files. Hosting is archive.org's existing file serving. Each index version never changes, so it caches well.
  • Costs: every feature is designed around bytes and round trips. Anything that must touch every record (exact counts over millions of matches) is precomputed into a file, or estimated.
  • Limits: results are as fresh as the last published build. Big one-time downloads (a 29 MB facet file, a 135 MB language model) must load in the background and be cached.

3. What an item publishes

Every item publishes a small required core. Everything else is an optional module, declared in the item's manifest so a page knows what's available. A separate config, owned by the page, says how to present it; a checker compares the two, so a rebuild can't silently break a page.

5. Search by meaning

The live ETD page can also search by meaning: a small multilingual model runs in the browser, turns the query into numbers, and compares it with 18.2 million stored vectors grouped into clusters. It finds theses that share no words with the query, including in other languages. On the live page it costs 80–87 MB and 43 seconds per search once warm, and 128 seconds for the first.

Phase 1 is built. We ported it into the demo with no change to the item's files: the scan runs in a Web Worker and reads 6 clusters at a time instead of 4. It returns the same top 50 as the live page for 5 queries, including one in German, and it's about twice as fast on a cold start.

"sea ice", same proxy, same dayLive pageOur port
First search (cold)53.6 s27.2 s
Later searches (warm)18.4 s14.6 s

One run each, on a slow network day. With the live page's read settings our port took 49.1 s cold, so the gain comes from the parallel reads. The bytes per search are unchanged; cutting those needs the owner.

8. Decisions and risks

Decisions needed

  1. Adopt the file contract as the standard for in-browser item search, and name an owner for it and its version numbers. Recommendation: yes. The ETD index owner is the natural first reviewer.
  2. Where the engine lives: inside collection-browser (today) or its own package. Recommendation: its own package once it reads the manifest, so pages other than collection-browser can use it.
  3. Ask the ETD index owner for CORS-readable file names, published layouts, a text-to-vector map, and leaner vector codes. Recommendation: one request, CORS first, since it blocks shipping. A draft is ready.
  4. Search by meaning in the product: cheap re-ranking of word results first, full meaning search later. Recommendation: yes to both, in that order; full search only after the owner publishes smaller codes.
  5. Estimated facet counts: may a facet show estimates on large result sets (clearly labelled)? Recommendation: yes, for items without exact facet files, with filtering limited or labelled.

Publishing rules

  • Version every file and publish the manifest last, so a client never mixes builds or sees files still uploading.
  • Keep a CORS-readable extension last. archive.org sends the cross-origin header by file type; ETD's names end in the version (dict.dir.20261026-5e5902), so only current.json is readable from other sites today.
  • Fixed sizes and record-aligned directories, so reading one record's data is arithmetic plus one range read.
  • Never reuse a key; renamed fields get new names so the checker catches them.

Engineering rules from ETD

  • Count requests, not just bytes: batch reads into multi-range requests.
  • Read in parallel; archive.org serves parallel range reads much faster than one stream. Reading 6 vector clusters at a time instead of 4, and splitting big ones, halved ETD's cold vector search.
  • Paint results as data arrives.
  • Load heavy files in the background, once, cached by index version.
  • Keep scoring and scanning in a Web Worker.
