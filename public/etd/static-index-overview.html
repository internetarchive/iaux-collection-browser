Static index search

Any archive.org item that publishes index files can be searched in the browser, with no search server. Here is where the four parts stand: the working ETD search, building indexes for other items, choosing those items, and the kinds of search we can offer.

As of 30 October 2026 · numbers measured on live items unless marked as estimates · Built merged and tested · Prototype run once, not shipped · Designed on paper · Open needs a decision

What a patron gets

  • Search 25.9 million theses from archive.org's own search page, with filters for year, language, country, degree and institution.
  • Find theses by meaning, including ones in other languages that share no words with the search.
  • Browse by filters alone, such as every thesis in Portuguese, with no search words.

All of it runs in the browser from files in the item, so there is no search server to keep up.

What changed in collection-browser

Only nine changes inside collection-browser itself, about 600 lines across 18 files (+612 −87). Everything else is new code beside it.

Needed to show a serverless search

  1. Plug in a different search service: the page supplies the search, so an engine in the browser answers instead of archive.org's search API
  2. Extra facet groups: a page adds filters collection-browser doesn't know, such as country, degree and institution
  3. Restore extra facets from the URL: shared links and Back keep those filters
  4. Refetch when the search service changes: switching Words and Meaning reloads the results

Better to match the live page

  1. Search by filters alone: browse with no search words, such as every thesis in Portuguese
  2. Refresh results in place: early meaning results, then refined without flashing
  3. A slot above the facets: room for the Words / Meaning switch
  4. A “service didn’t answer” message: a failed search no longer reads as “no results”
  5. Snippet highlight fix: no spaces added around highlighted words

Extra facet groups and search by filters alone are WEBDEV-9763 (PR #630, in review); the rest are on the ETD branch (PR #629). Each change with its original problem: the full proposal's Appendix F.

2Is a collection a good fit? Built

A good candidate is many records of one kind, each with an id and a link, mostly public and slow to change, with a real text field and two to four well-filled fields to filter by. Ten minutes with archive.org's search API answers most of it.

3Kinds of search Designed

The engine plugs into collection-browser through one search interface, so a new kind of search is a new source behind it, not a change to the interface. Two exist; the cheapest next ones need no new download.

SearchWhat it doesCost in the browserStatus
WordsWord-frequency scoring per field, plus words-close-together boost~2 requests, +6 for the boostBuilt
MeaningA small model in the browser; nearest clusters of stored vectors135 MB model once; 80–87 MB a searchBuilt
Filters onlyBrowse by facets with no wordsFacet data onlyBuilt
Leaner meaningSmaller stored vectors, then exact re-score~24–43 MB a search EstimateNeeds owner rebuildThe ETD owner rebuilds the compressed vector file (cell-codes.bin) with centred 1-bit or 2-bit codes instead of today's 4-bit ones. The engine already re-scores the best matches from the full vectors.
Quality priorsRank by signals like views or full text availableOne byte per recordNext
HybridMerge word and meaning rankings into one listArithmetic on two listsNext
Build-time expansionRelated words added at build time; meaning-like results with no modelStill a word searchLater
Graph vector searchHop between neighboursA round trip per hopAvoid

Recommended order: quality priors, then hybrid ranking, then build-time expansion. Each improves results without adding a large download.

Phases

  1. Option A, plus separate text and vector sources, so a local vector store can pair with etd-search's text index. Enough for laptop demos.
  2. One source list (archive.org items, dev-server folders, folders picked this visit) and search across sources, interleaving each source's results by rank with a source label, since scores from different indexes don't compare.
  3. Option B, only if reviewers need their own files on review apps.

Open

  • Just Isa on local dev, or reviewers too?

5Room to grow

Ideas that the parts we've built make cheap. Four stand out; six more are on the shelf.

  • ★ Top pick

    Search several items at once

    ETD, Democracy's Library and theses-and-dissertations in one result list, scores merged by rank.

    Builds on the multi-part index design for freshness

  • ★ Top pick

    A search box on any item page

    Search right where people already are: the item or collection page, wherever index files exist.

    Builds on the engine and one manifest per item

  • ★ Top pick

    Self-serve for uploaders

    Upload a dataset, get a search. No request to web dev.

    Builds on the setup form and the derive step

  • ★ Top pick

    Works anywhere, offline too

    The index is just files: a mirror, a torrent, or a cached tab with no connection. It is preserved with its data.

    Builds on static files read by byte range

Also on the shelf

  • Full text: the first pages of OCR text, for scanned collections like theses-and-dissertations
  • Related items: “more like this” from the meaning vectors
  • Search as of a date: each manifest points at the one before it
  • Lighter central search: big datasets stay out of the main search cluster
  • The engine in scripts: the same files, searched from Node
  • Type-ahead: prefix files for titles, creators, institutions

One claim to word carefully: queries never reach a search server, but the byte ranges a browser asks for can hint at the words searched. So: no query logs, rather than full privacy.

6Building and refreshing an index Prototype

ETD's files were built by hand and uploaded. For other items, archive.org needs a normal way to build them: a derive step that turns an item's records into index files, and keeps them fresh.

  • Setup form Designed: five steps (choose data, check records, fields, results and options, review and save). It runs in the browser and produces the two files an owner uploads. See the wireframes.
  • Builder Prototype: a TypeScript command-line tool next to the engine, run by a petabox derive rule in a container (the pattern already used 20+ times for OCR and speech). Outputs are registered through extra_targets.json.
  • Versioning Built in the client: every file carries its version; each build writes static-index.<v>.json and the publish step writes static-index.json pointing at the previous one. The browser checks every file's size against the item's own file list, so files republished at different times are caught.

Keeping it fresh

  • Weekly full rebuilds first Designed: a whole Democracy's Library rebuild takes about 17 minutes, nearly all of it exporting the records, so rebuilding everything once a week is enough to start. It's skipped when a cheap fingerprint (record count, latest change time) shows nothing changed.
  • Small additions later, only if needed Later: a base that never changes, up to about four small additions merged into one middle layer, and a full rebuild when that layer reaches about 10% of the base. Democracy's Library adds about 1,700–3,200 records a week, so it doesn't need this yet.
  • Real changes only: archive.org's change date moves about 20 times more often than records actually change, so each record's indexed fields are hashed and compared.
  • Takedowns: an uploaded removals list triggers a quick rebuild that drops those records; the weekly comparison catches the rest within 7 days.

Decisions needed

  • Takedowns: is hiding a record enough, or must its bytes be removed from the files?
  • Record ids: real archive.org identifiers, or positions (which change at each full rebuild)?
  • How a derive is told which kind of build to run: full, additions only, or removals only.
  • Infrastructure sign-off for the weekly trigger, worker memory and disk limits, and new file format names.
